# PROJECT ZERO LANCE
## 웹 기반 3D 횡스크롤 슈팅 게임 — 개발 프롬프트 v1.0

> 목표: Gradius V 수준의 설계 깊이를, 2026년 웹 기술(WebGPU)로 그 이상의 그래픽 품질로 구현한다.
> 배포 형태: 브라우저 URL 접속 즉시 플레이. PC/모바일 브라우저 공통. 설치 불필요.
> 작성 기준일: 2026년 9월

---

## 0. 이 문서 사용법

이 문서는 세 가지 용도로 쓰인다.

1. **3장 "마스터 프롬프트"** — AI 코딩 에이전트(Claude Code 등)나 외주 개발사에 그대로 전달하는 최상위 지시문
2. **4~14장 사양서** — 각 시스템의 확정 사양. 에이전트가 참조할 단일 진실 원천(Single Source of Truth)
3. **16장 스프린트 프롬프트** — 실제 개발을 순서대로 진행시키는 단계별 지시문

에이전트에 투입할 때는 **16장의 스프린트 프롬프트를 하나씩** 주고, 매번 "관련 장(4~14장)을 먼저 읽고 시작하라"고 지시한다. 문서 전체를 한 번에 주고 "다 만들어"라고 하면 품질이 무너진다.

## 1. 기술 조사 요약 및 결정 근거 (2026년 9월 기준)

### 1.1 왜 게임 엔진(Unity/Godot)이 아닌가

| 항목 | Unity WebGL | 판단 |
|---|---|---|
| 빌드 용량 | 10~50MB+ | 웹 첫 진입 이탈률 치명적 |
| 시작 속도 | 네이티브 웹 엔진 대비 느림 | 브라우저 게임의 최대 약점 |
| 모바일 브라우저 성능 | 알려진 문제점 | 본 프로젝트의 주 타깃이 모바일 |
| WebGPU | Unity 6에서 실험적, 기본 비활성 | 그래픽 품질 목표와 상충 |
| 웹 생태계 통합 | 약함 | 로그인/랭킹 웹 UI와 분리됨 |

Unity WebGL은 **이미 Unity 프로젝트가 있어서 브라우저 버전을 추가로 내는 경우**에만 합리적이다. 웹 우선(web-first) 신규 프로젝트에는 부적합하다.

Godot 4 웹 익스포트는 용량은 작지만 3D 렌더링 기능이 Unity/웹 전용 엔진 대비 얇고, WebGPU 대응이 늦다.

### 1.2 2026년에 판이 바뀐 지점: WebGPU

- **전 브라우저 베이스라인 달성**: Chrome 113+, Firefox 147+, Safari(macOS Tahoe 26 / iOS 26 / iPadOS 26 / visionOS 26)
- iOS 26의 Safari가 완전한 하드웨어 가속을 열면서, "iOS 때문에 WebGL 써야 한다"는 조언이 무효화됨
- 드로우콜 집약 / 컴퓨트 집약 시나리오에서 WebGL2 대비 **2~10배** 성능 향상
- 컴퓨트 셰이더로 파티클·컬링·물리를 GPU에서 처리 가능

즉, **탄막 슈팅에 필요한 "수천 개 오브젝트 + 대량 파티클 + 후처리"가 브라우저에서 처음으로 제대로 가능해진 시점**이 지금이다.

단, WebGPU를 baseline으로 삼되 **WebGL2 폴백은 반드시 유지**한다. 구형 안드로이드 단말의 롱테일이 남아 있다.

### 1.3 웹 3D 엔진 비교

| 엔진 | 런타임 크기 | WebGPU 성숙도 | 모바일 성능 | 자유도 | 학습·레퍼런스 |
|---|---|---|---|---|---|
| **Three.js** | ~168kB gzip | 무설정 WebGPU 렌더러 + WebGL2 자동 폴백 | 양호 | 최고 (아키텍처 강제 없음) | 최다 (주간 500만 DL) |
| **PlayCanvas** | 1~2MB | 웹 엔진 중 최고 성숙도 | 최고 (게임 목적 설계) | 중 (ECS 강제) | 중 |
| **Babylon.js** | 큼 | 우수 (9.0에서 클러스터드/볼류메트릭 라이팅) | 중 | 상 | 상 |

### 1.4 최종 결정

**주 스택: Three.js (WebGPURenderer + WebGL2 폴백) + TypeScript + Vite**

선정 이유:
1. 탄막 슈팅은 **커스텀 인스턴싱 렌더링과 커스텀 포스트프로세싱이 게임의 핵심**이다. 엔진이 아키텍처를 강제하지 않는 Three.js가 유리하다.
2. 번들이 가장 가벼워 웹 첫 진입 로딩 시간에서 유리하다.
3. 레퍼런스 밀도가 압도적이라 AI 에이전트 기반 개발 시 정확도가 가장 높다.
4. WebGPU/WebGL2 이중 대응이 라이브러리 레벨에서 자동 처리된다.

**대안(Plan B): PlayCanvas Engine (npm, 에디터 미사용 코드-퍼스트 모드)**
중저가 안드로이드 실기 테스트에서 목표 프레임을 못 맞출 경우 전환한다. 전환 비용을 낮추기 위해 **13장의 아키텍처 규칙(렌더러 추상화 계층)을 반드시 지킨다.**

### 1.5 백엔드 결정

**Supabase (PostgreSQL + Auth + Row Level Security + Edge Functions)**

- 요구사항인 "아이디/패스워드 로그인 + 스코어·최종레벨 이력 조회"에 정확히 맞는 관계형 모델
- 웹 클라이언트용 JS SDK가 1급 시민
- RLS로 "본인 이력만 조회" 정책을 DB 레벨에서 강제 가능
- Edge Function으로 서버측 스코어 검증 로직 배치 가능

**PlayFab 배제 사유(중요)**: 2026년 3월 11일 Microsoft가 Development Mode를 10만 MAU에서 **누적 1,000계정으로 축소**했고, 무료 대체안 Foundation Mode는 **Xbox 출시를 조건**으로 건다. 본 프로젝트(웹/모바일 전용)는 자격 미달이다.

**Unity Gaming Services 배제 사유**: Unity 엔진을 쓰지 않으므로 이점이 없다.

**대안**: Firebase(Auth + Firestore). 다만 스코어 이력 조회처럼 관계형 쿼리가 중심이면 Supabase가 적합하다.

### 2.1 절대 금지 사항

- **물리 엔진(Rapier, Cannon, Ammo) 도입 금지.** 탄막 슈팅의 충돌은 원-원 거리 판정이면 충분하며, 물리 엔진은 프레임 예산을 통째로 먹는다.

## 3. 마스터 프롬프트 (AI 에이전트 투입용)

> 아래 블록을 그대로 복사해 개발 에이전트의 최상위 지시문으로 사용한다.

```
당신은 웹 기반 3D 횡스크롤 슈팅 게임 "PROJECT ZERO LANCE"를 개발하는 시니어 게임 엔지니어다.

[제품 정의]
브라우저 URL 접속만으로 즉시 플레이 가능한 3D 횡스크롤 아케이드 슈팅 게임.
PC 브라우저와 모바일 브라우저 양쪽에서 16:9 꽉 찬 화면으로 60fps 구동되어야 한다.
게임플레이는 2D 평면(횡스크롤)이지만, 기체·적·배경은 전부 3D 모델과 3D 라이팅으로 렌더링한다.
레퍼런스는 Gradius V(Treasure/G.rev, 2004)이며, 그래픽 품질은 그것을 명확히 상회해야 한다.

[기술 스택 — 변경 금지]
- TypeScript(strict) + Vite
- Three.js WebGPURenderer 우선, WebGL2 자동 폴백
- 셰이더는 TSL로 작성하여 두 백엔드 모두 대응
- UI(로그인/메뉴/HUD/랭킹)는 React + Tailwind DOM 오버레이, 게임 루프와 완전 분리
- 백엔드는 Supabase (Auth + PostgreSQL + RLS + Edge Functions)
- 물리 엔진 사용 금지. 충돌은 자체 원-원/원-AABB 판정
- 탄과 적은 개별 Object3D 금지. InstancedMesh 기반 배치 렌더링

[절대 지켜야 할 성능 규칙]
1. 게임 루프(매 프레임 실행 경로) 안에서 객체를 new 하지 않는다. 모든 엔티티는 사전 할당된 풀(pool)에서 재사용한다.
2. 탄환은 구조체 배열(SoA: Structure of Arrays, Float32Array)로 관리하고, 렌더링은 InstancedMesh 단일 드로우콜로 처리한다.
3. 충돌 판정은 공간 해시(spatial hash) 브로드페이즈를 거친 뒤 정밀 판정한다. 전수 비교 금지.
4. 목표: 미들레인지 안드로이드(2023년 이후 출시 기준) 크롬에서 동시 탄환 1,500발 이상, 60fps 유지.
5. 매 스프린트 종료 시 실기 프로파일링 수치를 보고한다.

[절대 지켜야 할 게임 디자인 규칙]
1. 가독성이 난이도보다 항상 우선한다. 플레이어가 죽었을 때 "왜 죽었는지" 즉시 알 수 있어야 한다.
2. 적탄은 배경과 절대 혼동되지 않는 색상·발광 규칙을 따른다(5.4절 참조).
3. 피격 판정 원(hitbox)은 기체 외형보다 훨씬 작게 잡는다. "아슬아슬하게 피했다"는 감각이 이 장르의 핵심이다.
4. 모든 적 공격은 발사 전 텔레그래핑(예고 연출)을 갖는다.
5. 게임플레이 유효 영역은 화면비와 무관하게 항상 고정 16:9 비율로 유지한다. 넓은 화면이 유리해지면 안 된다.

[작업 방식]
- 각 스프린트 시작 전에 해당 스프린트가 참조하는 사양서 장(章)을 먼저 읽고, 구현 계획을 요약해 제시한 뒤 착수한다.
- 사양서와 충돌하는 구현을 하지 않는다. 사양이 불명확하면 임의로 정하지 말고 질문한다.
- 각 스프린트 종료 시 반드시 다음을 제출한다:
  (a) 동작하는 빌드
  (b) 실기 성능 측정치 (FPS, 드로우콜, 메모리, 로딩 시간)
  (c) 다음 스프린트로 넘기는 미결 항목 목록
- 임시방편(TODO, any 타입, 하드코딩 매직넘버)을 남길 경우 반드시 코드에 표시하고 보고서에 명시한다.

[품질 기준 — 이것을 만족하지 못하면 미완성이다]
- 첫 화면 표시까지 3초 이내 (4G 회선 기준)
- 로그인 후 게임 시작까지 클릭 3회 이내
- iOS Safari와 안드로이드 Chrome 실기에서 동일하게 동작
- 세로 모드에서는 "가로로 돌려주세요" 안내 표시
- 사운드는 최초 사용자 터치 시점에 언락 (브라우저 오토플레이 정책 대응)
```

## 4. 화면 · 해상도 · 입력 사양

### 4.1 화면비 및 레이아웃

```
기준 해상도    1920 x 1080 (16:9)
논리 좌표계    가로 32 units x 세로 18 units (월드 유닛)
               → 1 unit = 60px @1080p
게임플레이 영역 항상 16:9 고정. 이것이 "공정한 화면"의 기준선.
```

**화면비 대응 규칙**

| 디바이스 화면비 | 처리 |
|---|---|
| 정확히 16:9 | 그대로 |
| 더 넓음 (19.5:9, 20:9 등 최신 폰) | 게임플레이 영역은 16:9 유지, **좌우 여백에 3D 배경을 연장 렌더링**(레터박스 검은 띠 금지). 플레이어 이동 한계는 16:9 경계로 고정 |
| 더 좁음 (4:3 태블릿) | 상하 여백 배경 연장, 동일 원칙 |
| 세로 모드 | 게임 정지 + "가로 모드로 회전" 오버레이 |

이 방식이 중요한 이유: 최신 스마트폰은 대부분 19.5:9 이상이라 16:9로 레터박스를 치면 화면이 좁아 보인다. 배경을 연장해 **꽉 찬 화면**을 만들되, 게임 밸런스는 고정 영역으로 지킨다.

**Safe Area 처리**
- `env(safe-area-inset-*)` CSS 변수로 노치/다이나믹아일랜드 영역 회피
- HUD 요소는 safe area 내부에만 배치
- 게임플레이 영역은 safe area와 무관 (배경 연장 영역에 노치가 걸리도록)

### 4.3 입력 사양

**모바일 — 상대 드래그(Relative Drag) 방식으로 확정**

모바일 슈팅에서 절대좌표(터치한 지점으로 기체 순간이동) 방식은 게임을 망가뜨린다는 것이 커뮤니티 정설이며, 실제로 그렇게 구현한 모바일 이식작들이 혹평을 받았다. 프리폼 상대 드래그가 유일하게 검증된 정답이다.

```
좌측 화면 절반: 어디를 터치해도 됨. 손가락 이동량 × 감도 = 기체 이동량
              → 손가락이 기체를 가리지 않음 (이것이 핵심)
              → 감도 조절 슬라이더 필수 제공 (0.5x ~ 2.0x)
              → 화면 밖으로 손가락이 나가도 추적 유지 (pointercapture)

우측 화면 하단: 특수기술 버튼 3개 (반투명, 크기 조절 가능)
사격:          기본 오토파이어. 수동 사격 옵션 제공(설정)
옵션 제어:     우측 상단 전용 버튼 1개 (7.4절)
일시정지:      우측 최상단 작은 버튼
```

**PC**
```
이동: 방향키 / WASD / 마우스(상대 이동 모드 선택 가능)
사격: 자동 (수동 = Z 또는 좌클릭)
특수기술: 1, 2, 3 키
옵션 제어: Shift (홀드)
일시정지: ESC
```

**게임패드 (Gamepad API)**
```
좌스틱/D패드 이동, A 사격, X/Y/B 특수기술, RB 옵션 제어, Start 일시정지
연결 시 자동 감지 및 UI 아이콘 전환
```

### 4.4 입력 지연 관리

```
- Pointer Events는 requestAnimationFrame 밖에서 즉시 수집, 큐에 적재
- 게임 틱에서 큐를 소비 (이벤트 핸들러 안에서 게임 로직 실행 금지)
- 고정 타임스텝 시뮬레이션(60Hz) + 렌더 보간
- passive: false로 preventDefault 처리 (스크롤/줌/당겨서새로고침 차단)
- touch-action: none CSS 필수
```

## 5. 렌더링 및 그래픽 품질 사양

### 5.1 핵심 컨셉

> "2D 게임플레이 평면 위에서 벌어지는, 3D 영화 같은 장면"

카메라는 직교(Orthographic)가 아니라 **약한 원근(Perspective, FOV 28~35도)** 을 쓴다. 이유:
- 직교 투영은 평면적으로 보여 "3D 효과"가 죽는다
- 약한 원근이면 게임플레이 평면(z=0)은 거의 왜곡 없이 유지되면서, 전경/배경 레이어에 시차(parallax)와 깊이감이 생긴다
- Gradius V가 3D 모델을 쓰면서도 2D 플레이를 유지한 방식이 정확히 이것이다

```
카메라       PerspectiveCamera, FOV 30, z = 34 (게임플레이 평면 z=0 기준)
             → z=0 평면에서 가시 영역이 정확히 32 x 18 units가 되도록 거리 계산
레이어 구성  z = +6  : 전경 오브젝트 (스쳐 지나가는 구조물, 블러 처리)
             z =  0  : 게임플레이 평면 (플레이어, 적, 탄, 아이템, 지형 충돌체)
             z = -8  : 근배경 (지형 디테일)
             z = -25 : 중배경 (구조물 실루엣)
             z = -60 : 원배경 (성운, 스카이박스)
```

### 5.2 렌더 파이프라인

```
1. 오파크 패스 (Deferred-lite 또는 Forward+)
   - 기체/적/지형: PBR 머티리얼 (metalness/roughness/normal/emissive)
   - MRT로 Emissive 버퍼 분리 출력 (블룸 정확도 확보)

2. 트랜스페어런트 패스
   - 탄환: Unlit + Emissive, Additive 블렌딩, InstancedMesh
   - 파티클: GPU 시뮬레이션(WebGPU 컴퓨트) / WebGL2에선 CPU 폴백

3. 포스트 프로세싱 (순서 고정)
   a. Bloom (Emissive 버퍼 기준, 2단계 다운샘플 — 모바일 비용 절감)
   b. Chromatic Aberration (화면 가장자리만, 미세하게)
   c. Radial Blur (부스트/보스 등장 시에만 트리거)
   d. Color Grading (LUT 3D 텍스처, 스테이지별 룩 전환)
   e. Vignette
   f. FXAA (WebGPU 환경에선 TAA 검토)
   g. Screen Shake (셰이더가 아닌 카메라 오프셋으로 처리)
```

**품질 프리셋 3단계 (자동 감지 + 수동 변경 가능)**

| 프리셋 | 대상 | 해상도 스케일 | 블룸 | 그림자 | 파티클 상한 | 후처리 |
|---|---|---|---|---|---|---|
| High | WebGPU + 데스크톱/플래그십 | 1.0 | 3단계 | 동적 | 8,000 | 전체 |
| Medium | WebGPU 미들레인지 | 0.85 | 2단계 | 블롭만 | 3,000 | Bloom+CG+Vignette |
| Low | WebGL2 폴백 / 구형 | 0.7 | 1단계 | 없음 | 1,000 | Bloom만 |

자동 감지: 첫 3초간 프레임타임 측정 → 목표 미달 시 자동 강등. 강등은 조용히, 승격은 하지 않음(핑퐁 방지).

### 5.3 기체·적 비주얼 규격

**플레이어 기체**
```
폴리곤     8,000 ~ 12,000 tris (LOD 없음, 항상 화면 중앙 근처)
텍스처     2048x2048 KTX2 — BaseColor / ORM(Occlusion+Roughness+Metallic) / Normal / Emissive
셰이딩     PBR + 커스텀 림라이트(Rim Light) 추가
           → 림라이트는 선택이 아니라 필수. 어두운 배경에서 실루엣을 보장한다.
애니메이션 - 기울기: 상하 이동 시 롤(roll) ±25도, 스프링 보간
           - 엔진 불꽃: Emissive 강도 + 스케일 애니메이션, 가속 시 증폭
           - 피격: 0.15초 화이트 플래시 + 0.3초 반투명 깜빡임(무적 시간 시각화)
```

**적 유닛**
```
잡몹       800 ~ 2,000 tris. LOD 2단계. InstancedMesh 배치 (동종 적 단일 드로우콜)
중형       3,000 ~ 6,000 tris
보스       15,000 ~ 40,000 tris. 파괴 가능 파츠는 개별 메시로 분리
공통 규칙  - 모든 적은 Emissive 채널에 "약점부 발광" 표현
           - 피격 시 셰이더 유니폼으로 플래시 (머티리얼 인스턴스 새로 만들지 말 것)
           - 파괴 시 메시 교체 없이 디졸브 셰이더 + 파편 파티클
```

### 5.4 탄환 가독성 규칙 (타협 불가)

이 장르의 성패는 여기서 갈린다.

```
[색상 규칙 — 전 스테이지 공통, 예외 없음]
  적탄 (일반)     : 진홍 #FF2A3C — Emissive 강도 3.0
  적탄 (관통/위험) : 청백 #6FE8FF — Emissive 강도 4.0
  적 레이저       : 자홍 #FF3DD0
  플레이어 탄     : 담청/백 #B8E6FF — Emissive 강도 2.0
  아이템          : 금색 #FFD24A + 회전 하이라이트
  배경            : 위 색상들의 채도를 절대 사용하지 않음. 배경은 저채도 유지.

[형태 규칙]
  적탄은 구(sphere) 또는 캡슐. 플레이어 탄은 길쭉한 형태.
  → 색맹 사용자를 위해 색상만으로 구분하지 않음.

[레이어 규칙]
  모든 탄환은 depthTest: false, renderOrder 최상위.
  → 지형이나 적 뒤로 탄이 숨는 상황을 원천 차단.

[텔레그래핑 규칙]
  모든 적 발사는 0.3~0.5초 예고를 갖는다.
  - 발사구 Emissive 점멸 (3회)
  - 레이저류는 얇은 조준선 프리뷰 후 발사
  - 보스 대형 공격은 화면 가장자리 경고 아이콘 + 사운드 큐

[피격 판정]
  플레이어 히트박스: 기체 외형의 약 15% 크기 원 (반지름 0.12 unit)
  → 히트박스 시각화 옵션 제공 (설정에서 ON 시 기체 중앙에 작은 점 표시)
  적탄 히트박스: 시각 크기의 80%
  그레이즈(스치기) 판정: 히트박스 반지름 4배 이내 통과 시 스코어 배율 증가
```

### 5.5 "Gradius V를 넘어서기" 위한 추가 연출

원작이 PS2 하드웨어 한계로 못 했던 것들. 이것들이 차별화 포인트다.

1. **동적 조명**: 플레이어 탄/폭발이 실제로 주변 지형을 밝힌다 (WebGPU 클러스터드 라이팅, 동시 광원 32개까지)
2. **볼류메트릭 라이트 샤프트**: 동굴/함내 스테이지에서 광원이 안개를 통과하는 빛기둥
3. **화면 왜곡**: 대형 폭발 시 열왜곡(heat distortion), 보스 워프 시 공간 왜곡
4. **파괴 반응 배경**: 배경 구조물이 전투 여파로 실제로 부서지고 잔해가 게임플레이 평면 앞으로 날아옴(무해한 연출용)
5. **동적 카메라**: Gradius V는 카메라 고정이었다. 본작은 보스 등장/처치, 대형 이벤트에서 카메라가 짧게 줌·틸트·롤 한다. **단, 게임플레이 중 상시 흔들림은 금지**(가독성 훼손)
6. **머티리얼 반응**: 금속 표면이 근처 폭발광을 반사(스크린스페이스 반사 또는 라이트프로브 갱신)
7. **시간대/광원 전환**: 스테이지 중반 광원 색온도가 서서히 변해 긴장감 상승

## 6. 코어 게임플레이 사양

### 6.1 기본 규칙

```
시점            횡스크롤 (좌 → 우 진행). 특정 구간에서 스크롤 방향 변화 허용(9장)
플레이어 이동   상하좌우 자유 이동. 화면 좌측 25%~우측 90% 범위 제한
                이동 속도: 기본 8.0 unit/s (파워업으로 최대 14.0까지 상승)
                가속 곡선: 즉시 반응(관성 없음). 슈팅에서 관성은 사망 원인.
사격            오토파이어 12발/초 (레벨에 따라 증가)
지형 충돌       접촉 즉시 사망 (일부 스테이지). 지형 충돌 있는 구간은 진입 전 경고
시뮬레이션      고정 60Hz 타임스텝. 렌더는 가변, 보간 처리
```

### 6.2 목숨 / 크레딧 / 컨티뉴 (아케이드 사양)

```
1 크레딧 = 기체 3대
크레딧 선택 = 게임 시작 전 메뉴에서 버튼으로 1~9 선택 (요구사항 반영)
3대 전멸    = 남은 크레딧이 있으면 CONTINUE 카운트다운 (10초)
              → 버튼 입력 시 그 자리에서 부활, 기체 3대 재충전
              → 크레딧 0이면 GAME OVER
```

**컨티뉴 시 처리 규칙 (중요 — 여기서 게임의 성격이 결정된다)**

| 항목 | 처리 | 이유 |
|---|---|---|
| 스코어 | **유지** | 아케이드 관례 |
| 파워업 레벨 | **1레벨로 초기화** | 컨티뉴 페널티. 무한 컨티뉴 무쌍 방지 |
| 특수기술 | 장착 슬롯 유지, 충전량 0 | |
| 재개 위치 | 사망 지점 즉시 부활 (Revival Start 방식) | 체크포인트 롤백은 현대 유저에게 가혹함 |
| 랭킹 기록 | **사용 크레딧 수를 함께 기록** | 1CC(원코인 클리어) 판별용 — 이게 진짜 랭킹의 기준이 된다 |

**랭킹 분리 필수**: `1CC 랭킹`(크레딧 1개만 사용)과 `종합 랭킹`을 별도 탭으로 제공. 이것이 없으면 스코어 랭킹이 "돈/시간 많이 쓴 사람 순"이 되어 무의미해진다.

**일반 사망 시 처리**
```
- 사망 지점에서 1.5초 후 부활 (무적 2초, 반투명 점멸)
- 파워업 레벨 -2 단계 강등 (완전 초기화 아님. 학습 의욕 유지)
- 장착 옵션(멀티플) 전부 소실 → 필드에 회수 가능한 형태로 잠시 남김(3초)
- 특수기술 슬롯은 유지, 충전량은 절반으로
```

### 6.3 스코어 시스템

```
기본 격추         적 티어별 100 / 300 / 1,000 / 5,000점
그레이즈 보너스   탄을 스칠 때마다 배율 +0.01 (최대 x5.0), 피격 시 x1.0으로 리셋
노미스 보너스     스테이지 무피격 클리어 시 50,000점
파워 유지 보너스  스테이지 클리어 시 (현재 파워레벨 x 5,000)점
보스 격파 시간    빠를수록 보너스 (최대 100,000점)
아이템 미회수     회수하지 않고 화면 밖으로 나간 아이템 1개당 -500점 (아이템 회수 유도)
```

그레이즈 시스템을 넣는 이유: 회피만 하는 소극적 플레이가 아니라 **탄에 가까이 붙는 공격적 플레이를 보상**해야 슈팅이 재미있어진다.

### 6.4 동적 난이도(Rank) 시스템

Gradius 시리즈의 숨은 핵심 메커니즘. 플레이어가 잘하면 게임이 조용히 어려워진다.

```
Rank 값: 0 ~ 100 (내부 수치, 유저에게 비공개)

상승 요인:  파워 레벨 상승 (+2/레벨)
            무피격 지속 시간 (+1 / 10초)
            격추율 높음 (+1 / 20킬)
하락 요인:  피격 (-15)
            컨티뉴 (-40)

Rank 반영:  적탄 속도      x(1.0 ~ 1.35)
            적 발사 빈도    x(1.0 ~ 1.5)
            적 배치 밀도    3단계 변형 테이블
            보스 페이즈 전환 속도

제한:       스테이지 시작 시 Rank의 30%를 감쇠 (누적 지옥화 방지)
            최대치에서도 "클리어 불가능"해지지 않도록 상한 검증 필수
```

## 7. 무기 · 파워업 · 특수기술

### 7.1 무기 3계열 (요구사항 직접 반영)

게임 시작 전 또는 스테이지 사이에 1개 선택. 각 계열은 8레벨까지 성장.

| 계열 | 특성 | 강점 | 약점 |
|---|---|---|---|
| **LASER (레이저)** | 관통 빔. 직선상 모든 적 관통 | 단일 표적 DPS 최고, 보스전 유리 | 화면 커버리지 최악, 잡몹 처리 힘듦 |
| **MISSILE (미사일)** | 유도 + 지면 폭발. 자동 추적 | 화면 전체 커버, 지상/후방 대응 | 순간 화력 낮음, 유도 지연 |
| **SPREAD (원형포탄)** | 방사형 확산탄. 부채꼴 다중 발사 | 근거리 화력, 다수 적 동시 처리 | 원거리 명중률 저하, 탄 확산 |

**레벨별 성장 테이블 예시 (LASER)**

Gradius V의 정체성이자 이 게임의 전략적 깊이를 담당하는 부분. 원작은 4종 제어 타입을 제공했다.

```
옵션 = 플레이어를 따라다니며 동일 무기를 함께 발사하는 무적 유닛. 최대 4기.
       옵션 1기당 화력 +100% (4기면 총 화력 5배)
```

**옵션 제어 모드 4종 — 게임 중 전용 버튼으로 순환 전환**

| 모드 | 동작 | 전술적 용도 |
|---|---|---|
| **TRAIL (기본)** | 플레이어 이동 경로를 뱀처럼 후행 | 무난. 초보자용 |
| **FREEZE** | 버튼 홀드 중 현재 위치에 고정 | 옵션을 위험지대에 배치해두고 본체는 안전지대로 이탈 |
| **DIRECTIONAL** | 버튼 홀드 중 발사 방향을 스틱 방향으로 고정 | 후방/상하 적 대응 |
| **ROTATE** | 버튼 홀드 중 플레이어 주위를 공전 | 근접 전방위 방어 및 공격 |

**이 시스템의 설계 의도**: 같은 스테이지를 다른 옵션 모드로 플레이하면 완전히 다른 게임이 된다. 반복 플레이 동기의 핵심.

### 7.4 특수기술 (요구사항 직접 반영)

```

발동         전용 버튼 / 키. 발동 후 충전 필요
충전 방식    적 격파 시 충전 게이지 상승 (기술별 필요량 상이)
             → 쿨다운 시간이 아니라 "적을 잡아야 충전"되는 구조.
                소극적 플레이를 억제하고 공격을 유도한다.
```

**특수기술 6종**

| # | 이름 | 효과 | 지속 | 충전 필요 | 등장 스테이지 |

| 2 | **REFLECT FIELD** | 접촉한 적탄을 흡수 후 반사탄으로 전환 | 5초 | 50킬 | 2 |
| 3 | **PHASE DASH** | 지정 방향 무적 돌진, 관통 대미지 | 즉발 | 25킬 | 3 |

| **T5 보스** | 다단 페이즈 | 2,000~12,000 | 스테이지 종료 |

### 8.2 적 AI 규칙

```
1. 모든 적은 등장 → 행동 → 이탈의 3단계 스크립트를 갖는다. 무한 배회 금지.
2. 편대(T0)는 "패턴"으로 배치한다. 랜덤 스폰 금지.
   → 반복 플레이 시 암기와 최적화가 가능해야 하며, 이것이 슈팅의 학습 재미다.
3. 조준탄(aimed shot)과 고정탄(fixed pattern)을 섞는다.
   → 조준탄만 쓰면 플레이어가 유인으로 무력화시킬 수 있다.
4. 화면 밖에서는 시뮬레이션하지 않는다 (진입 트리거 방식).
5. 적 배치는 데이터(JSON)로 분리한다. 코드에 하드코딩 금지.
   → 레벨 디자인 이터레이션 속도가 게임 완성도를 결정한다.
```

### 8.3 보스 설계 원칙

```
공통 구조    페이즈 3단계 (HP 100~60% / 60~25% / 25~0%)
             페이즈 전환 시 무적 연출 2초 + 패턴 완전 교체
             파괴 가능 파츠 (포탑/날개/장갑) 존재 — 파괴 시 해당 패턴 소멸

             "대량"은 무작위 난사가 아니라 "읽을 수 있는 밀집 패턴"이어야 한다

제한시간     3분. 초과 시 보스가 도주하고 스테이지 클리어(보너스 없음)
```


### 9.1 스테이지 데이터 구조

모든 스테이지는 코드가 아니라 **데이터 파일**로 정의한다.

```typescript
interface StageData {
  id: number;
  name: string;
  durationSec: number;
  scrollSegments: ScrollSegment[];   // 방향/속도 구간
  terrain: TerrainChunk[];           // 지형 충돌 폴리라인
  spawns: SpawnEvent[];              // { timeSec, enemyType, x, y, pattern, count }
  items: ItemPlacement[];
  bossId: string;
  lighting: LightingProfile;         // 광원 색/강도/시간축 애니메이션
  postFx: PostFxProfile;             // LUT, 블룸 강도 등 스테이지별 룩
  bgm: string;
}
```

레벨 디자이너(또는 기획자)가 코드 수정 없이 JSON만 고쳐 이터레이션할 수 있어야 한다. 가능하면 간단한 웹 기반 스테이지 에디터를 별도 툴로 만들 것(스프린트 7).

## 10. 게임 플로우 및 화면 구성

### 10.1 전체 플로우

```
[진입]
  URL 접속
```

### 11.2 데이터베이스 스키마

```sql
-- 프로필
create table profiles (
  id            uuid primary key references auth.users(id) on delete cascade,
  username      text unique not null check (char_length(username) between 3 and 16),
  display_name  text,
  created_at    timestamptz default now()
);

-- 플레이 세션 (요구사항: 스코어와 최종 레벨 이력 조회)
create table play_sessions (
  id              bigserial primary key,
  user_id         uuid not null references profiles(id) on delete cascade,
  score           bigint not null check (score >= 0),
  final_stage     smallint not null check (final_stage between 1 and 6),
  final_substage  text,                    -- 예: "5-B"
  final_power_lv  smallint not null,       -- 요구사항: 최종 레벨
  weapon_type     text not null,           -- LASER / MISSILE / SPREAD
  credits_used    smallint not null,       -- 1이면 1CC
  cleared         boolean not null default false,
  max_graze_mult  numeric(4,2),
  play_time_sec   integer not null,
  kill_count      integer not null,
  client_version  text not null,
  session_hash    text not null,           -- 서버 검증용
  created_at      timestamptz default now()
);

create index idx_sessions_user_created on play_sessions(user_id, created_at desc);
create index idx_sessions_score        on play_sessions(score desc);
create index idx_sessions_1cc          on play_sessions(score desc) where credits_used = 1;

-- RLS 정책
alter table play_sessions enable row level security;

create policy "본인 이력만 조회"
  on play_sessions for select
  using (auth.uid() = user_id);

create policy "삽입은 Edge Function만"
  on play_sessions for insert
  with check (false);        -- 클라이언트 직접 삽입 차단. service_role만 허용.

-- 랭킹은 별도 뷰로 공개
create view public_ranking as
  select p.username, s.score, s.final_stage, s.final_power_lv,
         s.weapon_type, s.credits_used, s.cleared, s.created_at
  from play_sessions s join profiles p on p.id = s.user_id
  order by s.score desc;
```

### 11.3 스코어 검증 (웹 게임의 필수 방어선)

웹 클라이언트는 전부 뜯어볼 수 있다. 클라이언트가 보낸 점수를 그대로 믿으면 랭킹은 하루 만에 무너진다.

```
[Edge Function: submit-session]

1. JWT 검증 → user_id 확정
2. 값 범위 검증 (sanity check)
   - score <= 이론적 최대치(스테이지별 상한 테이블 합)
   - play_time_sec >= 도달 스테이지별 최소 소요 시간
   - kill_count <= 스테이지별 최대 배치 적 수 합계
   - final_power_lv <= 8
   - credits_used <= 9
3. 세션 무결성
   - 게임 시작 시 서버에서 session_token 발급 (스테이지 시드 포함)
   - 종료 시 토큰 + 입력 이벤트 요약 해시 제출
   - 토큰 만료(최대 90분) / 재사용 차단
4. 이상 탐지
   - 동일 유저 5분 내 3회 이상 제출 → 플래그
   - 개인 최고 기록 대비 300% 초과 → 플래그 (자동 차단 아님, 검토 큐)
5. 통과 시 service_role로 insert

[추가 방어 — 선택]
   상위 랭킹 진입 세션은 입력 로그(프레임별 입력)를 함께 제출받아
   서버에서 결정론적 리플레이 재현으로 검증.
   → 게임 시뮬레이션을 완전 결정론적으로 설계해야 가능(13.4절).
     초기부터 이 구조로 만들어두면 나중에 붙이기 쉽다.
```

### 12.4 자주 발생하는 함정

```
1. 머티리얼 인스턴스 남발
   → 피격 플래시를 위해 material.clone() 하면 셰이더 재컴파일로 프레임 드랍.
     반드시 InstancedBufferAttribute 또는 유니폼으로 처리.

2. 셰이더 컴파일 히칭
   → 스테이지 로딩 시 모든 머티리얼을 화면 밖에서 1프레임 렌더해 워밍업.
     renderer.compileAsync() 사용.

3. iOS Safari 메모리 강제 종료
   → 탭 메모리 상한이 낮다. 스테이지 전환 시 이전 스테이지 에셋 명시적 dispose.
     geometry.dispose(), texture.dispose(), renderer.info로 누수 모니터링.

4. 오디오 언락
   → 브라우저 오토플레이 정책. 최초 사용자 제스처에서 AudioContext.resume().
     타이틀 화면의 "TOUCH TO START"가 이 역할을 겸한다.

5. 배경 탭 전환
   → visibilitychange에서 게임 일시정지 + AudioContext 서스펜드.
     안 하면 복귀 시 deltaTime 폭발로 모든 오브젝트가 순간이동한다.

6. 고주사율 디스플레이(120Hz)
   → 고정 60Hz 시뮬레이션 + 렌더 보간 구조가 아니면 게임 속도가 2배가 된다.
```

### 13.3 게임 루프

```typescript
const FIXED_DT = 1 / 60;
let accumulator = 0;

function frame(now: number) {
  const raw = (now - last) / 1000;
  last = now;
  // 탭 복귀 시 deltaTime 폭발 방지
  accumulator += Math.min(raw, 0.25);

  inputManager.flush();                 // 큐에 쌓인 입력을 게임 상태로 반영

  while (accumulator >= FIXED_DT) {
    gameState.tick(FIXED_DT);           // 결정론적 시뮬레이션
    accumulator -= FIXED_DT;
  }

  const alpha = accumulator / FIXED_DT;
  visual.sync(gameState, alpha);        // 보간 렌더
  renderer.render();

  requestAnimationFrame(frame);
}
```

### 13.4 결정론(Determinism) 요구사항

서버측 리플레이 검증과 재현 가능한 버그 리포트를 위해 시뮬레이션은 완전 결정론적이어야 한다.

```
- Math.random() 사용 금지. 시드 기반 PRNG(xorshift128 등)만 사용.
- 시드는 게임 시작 시 서버가 발급.
- 시뮬레이션은 고정 타임스텝만 사용. deltaTime 가변값을 로직에 넣지 않는다.
- 부동소수 연산 순서를 프레임마다 동일하게 유지 (배열 순회 순서 고정).
- 입력은 프레임 번호와 함께 기록 → { frame, inputBits } 배열이 곧 리플레이.
```
